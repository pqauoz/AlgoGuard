ALGOGUARD USER MANUAL AND DATA GUIDE
====================================

This guide explains how to use AlgoGuard from start to finish, including what
data to upload, what values to put in the Simulation page, and what happens if
the system detects an anomaly.


1. WHAT ALGOGUARD DOES
----------------------

AlgoGuard is a web application that demonstrates network anomaly detection.

It has two main modes:

1. Dataset Mode
   Upload a CSV dataset, train machine learning models, compare the results,
   and identify the best model.

2. Simulation Mode
   Type one network traffic example manually and let the pretrained model
   classify it as Normal or Attack.

Important:
AlgoGuard is a simulation/prototype. It does not capture live network packets
from your Wi-Fi or LAN. It analyzes CSV files and manual inputs.


2. HOW TO RUN ALGOGUARD
-----------------------

Open a terminal in the project folder:

C:\Users\Client\Documents\AlgoGuard

Then run:

venv\Scripts\activate
python -m pip install -r requirements.txt
python app.py

if python is not on path, run with the existing virtual environment
.\venv\Scripts\python.exe app.py

Then open:

http://localhost:5000

Default local login:

Username:
admin

Password:
admin123

Important:
The default admin is created only when the local SQLite database is first
created. For a real deployment, change the admin username/password using
environment variables before the first run.

After logging in with an Administrator account, open the Admins page to create
more admin accounts. Each new admin is stored in SQLite with a hashed password.

If port 5000 is busy:

set ALGOGUARD_PORT=5001
python app.py

Then open:

http://localhost:5001


3. WEBSITE PAGES
----------------

Login
    Opens the protected admin entry page. You must sign in before using the
    Dashboard, Upload, Results, or Simulation pages.

Admins
    Allows an Administrator account to create and review multiple admin
    accounts.

Dashboard
    Shows the AlgoGuard overview, latest dataset result, normal/anomaly
    counts, and best model after training.

Upload
    Uploads a CSV dataset and trains models.

Results
    Shows the model comparison table after dataset training.

Simulation
    Lets you manually type one network flow and predict if it is Normal or
    Attack.

-------------------------------------

The uploaded file must be a CSV file.

The last column must be the target label.

Example:

dur,rate,proto,state,sbytes,dbytes,label
0.10,12,tcp,CON,500,420,normal
0.01,5000,tcp,REQ,2000,60,attack

In this example:

Features:
    dur
    rate
    proto
    state
    sbytes
    dbytes

Target label:
    label

The target label is the answer that tells the model whether the row is normal
or attack/anomaly.

6. WHAT NORMAL DATA CAN LOOK LIKE
---------------------------------

Normal traffic usually has values that look moderate and consistent.

Example normal row:

dur,rate,proto,state,spkts,dpkts,sbytes,dbytes,sttl,dttl,label
0.10,12,tcp,CON,12,9,500,420,64,64,normal

Meaning:

dur
    The connection duration. 0.10 means short but not extreme.

rate
    Packets per second. 12 is a moderate value.

proto
    Protocol. tcp or udp are common.

state
    Connection state. CON or FIN can appear in normal traffic.

spkts and dpkts
    Source and destination packet counts.

sbytes and dbytes
    Source and destination byte counts.

sttl and dttl
    Time-to-live values. Normal traffic often uses reasonable TTL values such
    as 64.

label
    normal


7. WHAT ANOMALY DATA CAN LOOK LIKE
----------------------------------

Anomaly or attack-like traffic often has unusual/extreme values.

Example anomaly row:

dur,rate,proto,state,spkts,dpkts,sbytes,dbytes,sttl,dttl,label
0.01,5000,tcp,REQ,1,1,2000,60,254,0,attack

Why this can look suspicious:

rate = 5000
    Very high packet rate.

state = REQ
    A request state that may indicate incomplete or suspicious communication.

sttl = 254
    High source TTL can appear in some attack patterns.

dttl = 0
    Destination TTL of 0 can look abnormal depending on the dataset.

sbytes much larger than dbytes
    One-sided traffic can sometimes indicate suspicious behavior.

label = attack
    This tells the training workflow that this row is an anomaly/attack.


8. WHAT HAPPENS IF YOU PUT AN ANOMALY IN THE DATASET
----------------------------------------------------

If your CSV contains anomaly rows, AlgoGuard uses them during training and
testing.

Example:

normal rows teach the model what normal traffic looks like.
attack rows teach the model what suspicious traffic looks like.

After upload, AlgoGuard:

1. Reads the CSV.
2. Treats the last column as the label.
3. Counts normal and anomaly rows.
4. Encodes text columns like proto and state.
5. Scales numerical values.
6. Splits the data into training and testing sets.
7. Trains Random Forest, Gradient Boosting, and Voting Classifier.
8. Tests each model.
9. Shows the metrics.
10. Saves model records and report metadata in SQLite.
11. Chooses the best-performing model.

If the model predicts anomaly correctly:
    Recall and F1-score may improve.

If the model predicts normal traffic as anomaly:
    False Positive Rate increases.

If the model misses actual anomalies:
    Recall may decrease.


9. WHAT HAPPENS IF ALL DATA IS NORMAL
-------------------------------------

The app will reject the dataset if the target label has only one class.

Example bad dataset:

dur,rate,proto,state,label
0.10,12,tcp,CON,normal
0.20,10,udp,CON,normal
0.15,11,tcp,FIN,normal

Why it is rejected:
The model needs at least two classes to learn classification.

Good dataset:
Must have at least:

- one normal class
- one attack/anomaly class

Also, each class should have enough rows for train/test split.


10. WHAT HAPPENS IF ALL DATA IS ATTACK
--------------------------------------

This is also invalid for training.

The model cannot learn the difference between normal and attack if it only sees
attack rows.

The dataset should contain both normal and attack/anomaly examples.

12. IMPORTANT CSV RULES
-----------------------

Rule 1:
The file must end with .csv.

Rule 2:
The file must have at least two columns:

- one or more feature columns
- one target label column

Rule 3:
The target label must be the last column.

Rule 4:
The target column must not be empty.

Rule 5:
The target column must contain at least two classes.

Rule 6:
Each class should have enough rows for training/testing.

Rule 7:
Text columns are allowed.

Example:
proto,state

Rule 8:
Numerical columns are allowed.

Example:
dur,rate,sbytes,dbytes

14. BAD CSV EXAMPLES
--------------------

Bad example 1: no target label

dur,rate,proto,state
0.10,12,tcp,CON
0.01,5000,tcp,REQ

Problem:
The app assumes the last column is the label, so it would treat "state" as the
target by mistake.

Bad example 2: only one class

dur,rate,proto,state,label
0.10,12,tcp,CON,normal
0.20,10,udp,CON,normal

Problem:
Only normal exists. The model needs normal and attack/anomaly.

Bad example 3: empty labels

dur,rate,proto,state,label
0.10,12,tcp,CON,
0.01,5000,tcp,REQ,attack

Problem:
The target label column has missing values.

Bad example 4: too few rows

dur,rate,proto,state,label
0.10,12,tcp,CON,normal
0.01,5000,tcp,REQ,attack

Problem:
Too few rows for a reliable train/test split.

18. WHAT HAPPENS IF SIMULATION DETECTS AN ATTACK
------------------------------------------------

If the Simulation page predicts Attack:

1. The result card shows Attack.
2. The confidence percentage is displayed.
3. The entered flow values are shown.
4. The traffic flow is saved in the network_traffic table.
5. The model result is saved in the prediction table.
6. An alert record is created in the alert table.

Future improvement:
Add an Alert History page so admins can review saved alert records directly
inside the web interface.


19. WHAT HAPPENS IF SIMULATION DETECTS NORMAL
---------------------------------------------

If the Simulation page predicts Normal:

1. The result card shows Normal.
2. The confidence percentage is displayed.
3. The entered flow values are shown.
4. The traffic flow and prediction are saved in SQLite.

This means the pretrained model thinks the flow is closer to normal traffic
than attack traffic.


20. WHAT CONFIDENCE MEANS
-------------------------

Confidence is the model's estimated certainty.

Example:

Prediction:
Attack

Confidence:
82.50%

Meaning:
The model is 82.50% confident in the predicted class.

Important:
High confidence does not guarantee the prediction is correct. It only shows
how confident the model is based on what it learned.

22. BEST MODEL SELECTION
------------------------

AlgoGuard chooses the best model using:

1. Higher F1-score
2. Higher accuracy
3. Lower false positive rate
4. Lower processing time

The best model is shown on the Dashboard and Results page.


23. WHAT FILES ARE CREATED AFTER TRAINING
-----------------------------------------

After uploading and training, the app can generate:

saved_models/random_forest.joblib
saved_models/gradient_boosting.joblib
saved_models/voting_classifier.joblib
reports/model_report_YYYYMMDDHHMMSS.csv
database/algoguard.sqlite3

These generated files are ignored by Git so the repository stays clean.

The SQLite database stores:

admin
    Multiple admin login accounts with hashed passwords.

network_traffic
    Traffic rows created from manual simulation or future dataset capture.

detection_model
    Trained model names, versions, metrics, training time, and model size.

prediction
    Prediction result, confidence score, timestamp, traffic reference, and
    model reference.

alert
    Attack/anomaly alerts created from suspicious predictions.

report
    Report metadata connected to the admin who generated the report.

report_alert
    Join table that can connect reports to one or more alert records.

system_log
    Login, logout, upload, training, and simulation activity records.


24. HOW TO EXPLAIN THIS IN A PRESENTATION
-----------------------------------------

Short explanation:

AlgoGuard is a lightweight anomaly detection prototype for network traffic.
It allows users to upload a CSV dataset, automatically preprocesses the data,
trains three ensemble machine learning models, compares their performance, and
identifies the best model. It also includes a manual Simulation page where a
single network flow can be classified as Normal or Attack using pretrained
model artifacts from artifacts/pretrained.

If asked if it monitors real traffic:

No. The current version is a simulation prototype. It does not capture live
network packets yet. It demonstrates the machine learning pipeline using CSV
datasets and manual flow input.

If asked what happens when an anomaly is detected:

The app displays the anomaly/attack result and confidence score. In Simulation
Mode, the traffic record, prediction record, and alert record are saved in
SQLite. In Dataset Mode, anomaly counts and model performance are shown in the
dashboard and results table. Real-time notifications and a full Alert History
page are planned future enhancements.

29. WHAT THE CSV COLUMNS MEAN
-----------------------------

This sample CSV has five columns:

dur
    Short for duration.
    It represents how long the network flow lasted.

    Example:
    0.10

    A small value means the flow happened quickly.

rate
    Represents traffic rate, such as packets per second.

    Example:
    12

    A moderate value can look normal.
    A very high value, such as 5000, can look suspicious.

proto
    Short for protocol.
    It tells what network protocol was used.

    Example values:
    tcp
    udp
    icmp

state
    Represents the connection state.

    Example values:
    CON
    FIN
    REQ
    INT

    CON or FIN can look more normal.
    REQ or INT can sometimes appear in suspicious traffic depending on the
    dataset.

label
    This is the target label.
    It tells the model the correct answer for that row.

    Example values:
    normal
    attack

    Important:
    In AlgoGuard, the label column must be the last column.


30. WHAT EACH SAMPLE ROW MEANS
------------------------------

Header row:

    This row is marked as normal traffic.

Attack row example:

dur = 0.01
    The traffic flow was very short.

rate = 5000
    The traffic rate is very high.

proto = tcp
    The flow used TCP.

    The connection state is REQ.

label = attack
    This row is marked as suspicious/attack traffic.

had an INT state, and is labeled as attack."


32. WHY THE CSV NEEDS NORMAL AND ATTACK ROWS
--------------------------------------------

The model learns by comparing examples.

Normal rows teach the model:

"This is what safe traffic can look like."

Attack rows teach the model:

"This is what suspicious traffic can look like."

If the dataset only has normal rows, the model cannot learn what attack traffic
looks like.

If the dataset only has attack rows, the model cannot learn what normal traffic
looks like.

That is why a good training CSV needs both normal and attack rows.
